\section*{Introduction}
These notes capture the primary insights and structural concepts learned while studying the implementation of a language model from scratch using the Rust programming language \cite{README.md, Rust_ML__Building_an_LLM_using_Rust_.pdf}.

\section{Part 1: The Tokenizer}

The tokenization phase establishes the groundwork for the language model by addressing three core dimensions:
\begin{enumerate}
    \item Converting text to numbers using Byte Pair Encoding (BPE).
    \item Understanding how this step directly shapes everything the model can and cannot do.
    \item Analyzing how different vocabulary sizes affect compression, processing speed, and training behavior.
\end{enumerate}

\subsection{Core Concepts \& Definitions}
\begin{enumerate}
    \item \textbf{Tokenizer:} A specialized tool used to convert human-readable text into numerical tokens.
    \item \textbf{BPE:} The specific subword algorithm used during the tokenization process.
    \item \textbf{Feste:} The name of the GPT-2 style language model being constructed.
    \item \textbf{Transformer:} The foundational deep learning architecture underpinning the language model.
    \item \textbf{Shakespeare:} The dataset source. The model is actively trained on the complete works of William Shakespeare.
\end{enumerate}

\subsection{Learning about the Transformer Architecture}
A transformer is a deep learning architecture integrated into a language model. It relies on an encoding-decoding structure and is driven by the \emph{Attention Mechanism}.

\subsubsection{What is the Attention Mechanism?}
This method determines the mathematical relationships between multiple words within a sentence, determining how they correlate with one another. 

Unlike conventional neural networks (such as RNNs or CNNs) which process data sequentially---incurring substantial time and storage penalties---the transformer model processes massive strings of data points in parallel. This parallelism accelerates operations like relevance mapping, encoding, and decoding.

\subsubsection{Key Features of the Model}
\begin{itemize}
    \item \textbf{Long-Range Context:} The model can maintain contextual relevance across long sequences.
    \item \textbf{Parallel Feature Processing:} Parameters like grammar, emotional tone, and syntax are processed concurrently.
    \item \textbf{Multi-Head Self-Attention:} Designed for uncovering and maintaining semantic relationships between disparate words.
    \item \textbf{Positional Encoding:} Injects structural ordering metadata into word vectors to preserve word sequences.
\end{itemize}
\emph{Example:} In the sentence \emph{``Ramu goes to temple in his village,''} the word \emph{``his''} refers to the name \emph{``Ramu''}. The model identifies this connection using its self-attention layer.

\subsubsection{Applications \& Benefits}
Transformers excel in specific real-world tasks such as training customer support chatbots and generating condensed medical report summaries. Their primary architectural benefits are long-range context handling, execution concurrency, and scalability.

\subsection{What Are We Building?}
The model, \textbf{Feste}, utilizes a GPT-2 style architecture built entirely in native Rust. While frameworks like TensorFlow or PyTorch abstract away the underlying mathematics to let developers focus strictly on higher-level architecture, using Rust introduces low-level control over memory management, performance optimization, absolute type safety, and strict ownership validation via the borrow checker.

\section{Why Tokenization Matters}
The boundaries of tokenization dictate what an LLM can ultimately achieve. Consider the following tokenization behavior over fragmented strings of the word \emph{``hello''}:
\begin{itemize}
    \item \texttt{["he", "llo"]} $\rightarrow$ mapped to Token IDs: 530 and 840 respectively.
    \item \texttt{[" he", "llo "]} $\rightarrow$ mapped to Token IDs: 460 and 670 respectively.
    \item \texttt{["ol", "leh"]} $\rightarrow$ mapped to Token IDs: 91 and 133 respectively.
\end{itemize}
Even though the underlying string represents the same word, the resulting Token IDs are completely disjointed. Because these variation boundaries prevent the neural network from effortlessly reversing or manipulating strings at a character level, word-level or unoptimized subword tokenization remains highly inefficient.

\section{The Byte Pair Encoding (BPE) Algorithm}
To resolve the limits of word-level tokenization, Feste defaults to a character/byte level where base tokens represent raw byte definitions. An 8-bit binary digit represents exactly 256 unique baseline values. Standard English characters consume 1 byte each, whereas complex items like emojis require up to 4 bytes. Each unique byte receives its own dedicated Token ID.

The BPE algorithm works by iteratively merging the most frequent adjacent tokens into entirely new, single tokens.
\\\emph{Example:} If the pair \texttt{"th"} repeats frequently across a text corpus, its individual character tokens (\texttt{'t'} and \texttt{'h'}) are systematically combined into a single new subword token, such as \texttt{344}. 

Consequently, common structural words consolidate into their own unique tokens, while rare terms break down into familiar base byte sequences that the tokenizer has observed across other training environments.
\begin{itemize}
    \item \textbf{Smaller Vocabularies:} Increase sequence length and fragmentation, forcing the model to construct phrases from tiny components.
    \item \textbf{Larger Vocabularies:} Preserve meaning per token and allow the network to discover conceptual relationships between sequential words more effectively, provided training is sufficient.
\end{itemize}

\section{Implementation Details}
The system begins with 256 unique entries mapping hex-encoded bytes to numerical IDs ($0$--$255$). During training, new token values are dynamically appended to the lexicon for every unique merge rule. These rules are maintained in an ordered vector, as execution order dictates application significance.

\subsection{Prefix Merge Ordering Example}
Before encoding a word like \texttt{"the"}, the tokenizer must step through its merge rules sequentially. For instance, it applies merge rule 1 ($M_1$) first to generate token \texttt{256} for the pair \texttt{"th"} ($\langle 74 \rangle\langle 68 \rangle$), before eventually applying merge rule 50 ($M_{50}$) which fuses token \texttt{256} with byte $\langle 65 \rangle$ (\texttt{'e'}) to generate the complete token \texttt{300}. 

This training pipeline is fully deterministic: it counts pairs, isolates the highest frequency pair, updates the corpus, and repeats without stochastic randomness.

\section{Training Performance \& Parallelization}
The computational bottleneck of BPE lies in counting adjacent token pairs across the training corpus. Instead of a single-threaded architecture, Feste implements the \texttt{Rayon} data-parallelism library in Rust to shard text data across multiple execution threads simultaneously.

\subsection{Parallel Chunk Boundary Constraints}
To prevent missing token merges that cross the split points between independent threads, a explicit \textbf{Boundary Check} is performed:
\begin{center}
    \texttt{Thread 1} $\rightarrow$ \texttt{[["t","h"] ["e","a","d"]]} \quad$\Longleftrightarrow$\quad \texttt{Thread 2} $\rightarrow$ \texttt{[["u","s"] ["e","d","t"]]}
\end{center}
Each thread checks its chunk boundary against the starting token of the adjacent chunk. This ensures spanning pairs (such as a split \texttt{"th"}, \texttt{"the"}, \texttt{"us"}, or \texttt{"used"}) are properly preserved and counted. Parallelization is purposefully restricted to pair-counting; executing the merges and updating the internal corpus is kept sequential to prioritize code legibility over over-engineered complexity.

For this educational model, chunks are processed independently; the loss in compression efficiency remains negligible, and BPE enforces strict rules against invalid boundary fracturing.

The baseline byte list is initialized as: $[\langle 54 \rangle, \langle 6f \rangle, \langle 20 \rangle, \langle 62 \rangle, \langle 65 \rangle]$. Assume the tokenizer has learned three ordered merge rules:
\begin{itemize}
    \item \textbf{$M_1$:} $\langle 6f \rangle\langle 20 \rangle \rightarrow \text{"o " } \rightarrow \text{Token } 256$
    \item \textbf{$M_2$:} $\langle 54 \rangle\langle 6f \rangle \rightarrow \text{"To" } \rightarrow \text{Token } 257$
    \item \textbf{$M_3$:} $\text{Token } 256 + \langle 62 \rangle \rightarrow \text{"o b" } \rightarrow \text{Token } 258$
\end{itemize}

The tokenizer processes these constraints sequentially:
\begin{enumerate}
    \item Applying $M_1$ transforms the original sequence into $[\langle 54 \rangle, 256, \langle 62 \rangle, \langle 65 \rangle]$.
    \item Applying $M_2$ attempts to find $\langle 54 \rangle\langle 6f \rangle$. Because the byte $\langle 6f \rangle$ was already consumed to create token \texttt{256} during the $M_1$ pass, the rule fails to match and the list remains unchanged.
    \item Applying $M_3$ scans for token \texttt{256} followed immediately by byte $\langle 62 \rangle$. This matches perfectly, compressing the collection into its final encoded array: $[\langle 54 \rangle, 258, \langle 65 \rangle]$.
\end{enumerate}

\section{Training Results \& Scaling Metrics}
Feste is evaluated across five distinct vocabulary sizes to understand performance changes. Production models (such as GPT-2 or GPT-3) scale much higher, maintaining a vocabulary threshold of $50,257$ tokens.

The performance of a tokenizer is measured by its \textbf{Compression Ratio (CR)}, which is defined as:
\begin{equation}
    CR = \frac{\text{Total Raw Bytes of Input Text}}{\text{Total Encoded Tokens Used}}
\end{equation}
A higher compression ratio reduces the sequence length passed into the transformer network, lowering active memory consumption and speeding up training loops.

These floating-point numbers are the actual parameters (weights) the model learns during training to understand relationships between tokens. \subsection{Trade-offs \& Diminishing Returns}
While expanding the vocabulary size increases the compression ratio, the gains scale with diminishing returns. This occurs because the initial iterations capture highly frequent, repeating character patterns. Once these core patterns are merged, subsequent rules target rare phrases or outliers that do not repeat often enough to significantly boost compression. Additionally, without advanced sampling optimizations, training time scales linearly with vocabulary size.

\subsection{The Data Scarcity Problem}
If an extensive vocabulary size (such as $1536$ or higher) is forced onto a relatively small training dataset, the tokenizer is forced to remember small phrases or rare word structures that appear only once. This leads to **embedding collapse**, causing the language model to interpret rare sequences as random statistical noise. Conversely, a very small vocabulary causes long sequence fragmentations, which slows down context processing. Selecting a vocabulary size proportionate to the dataset volume is vital.

\section{Strategic Architectural Choices}
The overarching design goal of Feste is to choose structural clarity over extreme performance optimization. Understanding how tokenization works step-by-step is prioritized over absolute execution speed.

\subsection{String-Based Token Representation Trade-offs}
Production tokenizers save memory by keeping merges mapped strictly as paired integers: $(\text{token\_a}, \text{token\_b}) = \text{new\_token}$. Feste, by contrast, deliberately retains hexadecimal character text representations ($\langle 66 \rangle, \langle 6f \rangle$) within its active token configurations.

\subsection{Vocabulary Management}
For plain English text, mapping token sequences to UTF-8 standards ensures perfect, error-free encoding and decoding cycles. However, this strategy is less optimized for non-English languages, which often require multiple bytes per character. Production-grade tokenizers (like \texttt{tiktoken\_rs}) address these multi-byte issues by pruning low-frequency merges. Feste, by contrast, purposefully retains all merge steps---including outliers---to ensure the entire pipeline can be audited.
